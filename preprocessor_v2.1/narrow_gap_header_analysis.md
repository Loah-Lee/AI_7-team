# 본문-헤더 폰트 크기 근접 케이스 대응 시 예상 문제점 분석

## 1. 문제 정의

sample28에서 확인된 현상:

| 폰트 크기 | span 수 | 문자 비율 | 현재 분류 |
|-----------|---------|----------|----------|
| 11.0pt | 2,932 | 42.7% | **본문** (body_size) |
| 12.0pt | 1,217 | 11.9% | 본문 취급 (임계값 미달) |
| 13.0pt | 1,360 | 18.2% | 본문 취급 (임계값 경계) |
| 14.0pt | 1,213 | 16.4% | 본문 취급 (char 비율 필터) |
| 15.0pt | 378 | 5.1% | 본문 취급 (char 비율 필터) |
| 32.0pt | 4 | 0.0% | **H2** |
| 82.8pt | 1 | 0.0% | **H1** |

현재 임계값 `body_size + 2.0 = 13.0pt`이므로 12pt는 후보에서 제외되고,
13~15pt는 후보에 진입하더라도 **문자 비율 15% 필터**에 의해 탈락한다.

실질적 구조 헤더(12~15pt)가 전부 본문으로 처리되어, 82.8pt(표지)와 32pt(장 구분)만 헤더로 검출됨.

---

## 2. 이 문제는 sample28에만 한정되지 않음

6개 샘플의 body와 바로 위 폰트 크기 간 gap:

| 샘플 | body | 최근접 상위 | gap | 해당 크기 문자 비율 |
|------|------|-----------|-----|-------------------|
| sample1 | 10.0 | 11.0 | **1.0pt** | 5.2% |
| sample5 | 11.0 | 12.0 | **1.0pt** | 10.1% |
| sample15 | 12.0 | 13.0 | **1.0pt** | 14.9% |
| sample28 | 11.0 | 12.0 | **1.0pt** | 11.9% |
| sample35 | 11.0 | 12.0 | **1.0pt** | 4.2% |
| sample61 | 13.0 | 13.8 | **0.8pt** | 0.0% |

body 바로 위 1pt 구간에 상당한 텍스트가 존재하는 파일이 다수.
이들 중 어떤 것이 진짜 헤더이고, 어떤 것이 강조/부제/표 셀인지는 폰트 크기만으로 구분 불가.

## 3. 대응 방안별 예상 문제점

### 방안 A: 임계값 축소 (`body_size + 2.0` → `body_size + 1.0` 이하)

**예상 문제**:

| 문제 | 설명 | 심각도 |
|------|------|--------|
| False positive 폭증 | body 11pt에서 12pt는 강조 텍스트, 표 헤더, 캡션, 각주 등 다양한 용도로 사용됨. 이들이 모두 헤더 후보에 진입 | 높음 |
| 기존 98개 파일 회귀 | 현재 정상 작동하는 파일에서 불필요한 헤더가 추가 검출되어 섹션이 과도하게 분할됨 | 높음 |
| 5개 필터 무력화 | 기존 필터(char 비율 15%, 평균 span 길이 80자, period_ratio 0.3)는 본문과 명확히 구분되는 헤더를 전제로 설계됨. 1pt 차이에서는 헤더 후보의 통계적 특성이 본문과 거의 동일하여 필터가 구분력을 상실 | 높음 |
| merge 충돌 | 현재 ≤0.5pt 이내를 같은 그룹으로 merge. gap이 1pt이면 merge는 안 되지만, 폰트 렌더링 jitter(±0.1~0.2pt)로 인해 11.0/11.2/11.8/12.0이 혼재할 경우 경계가 불명확 | 중간 |

### 방안 B: 볼드(bold) 속성을 헤더 검출 보조 신호로 추가

**예상 문제**:

| 문제 | 설명 | 심각도 |
|------|------|--------|
| 볼드 ≠ 헤더 | 표 셀 헤더, 강조 키워드, 범례 등도 볼드 사용. 볼드만으로 헤더를 결정하면 false positive 발생 | 중간 |
| 볼드 미사용 헤더 | 일부 RFP는 헤더에 볼드를 쓰지 않고 크기만 변경. 볼드 의존 시 이런 문서에서 헤더 누락 | 중간 |
| PyMuPDF 볼드 플래그 신뢰도 | HWP→PDF 변환 과정에서 볼드 플래그가 유실되거나 잘못 설정되는 사례 존재 | 낮음 |
| 규칙 복잡도 증가 | "크기 OR 볼드" 조합의 경우의 수가 증가하여 디버깅 난이도 상승 | 중간 |

### 방안 C: 번호 패턴 기반 헤더 검출 (`1.`, `가.`, `(1)`, `제N조` 등)

**예상 문제**:

| 문제 | 설명 | 심각도 |
|------|------|--------|
| 번호 목록과 구분 불가 | `1. 항목 내용`이 헤더인지, 본문 내 번호 목록인지 폰트 크기 없이는 판단 불가 | 높음 |
| 패턴 다양성 | 한국어 RFP의 번호 체계가 문서마다 상이 (`1.` / `Ⅰ.` / `가.` / `제1장` / `1-1` 등). 모든 패턴 커버는 비현실적 | 높음 |
| 표 내부 번호 | 표 셀 안에도 `1.`, `2.` 등이 빈번. 표 영역 제외 로직과의 상호작용 복잡 | 중간 |
| 한국어 특수성 | `제`, `조`, `항` 등의 법률/공공 문서 접두사를 하드코딩해야 하며, 일반화 곤란 | 중간 |

### 방안 D: 문자 비율 필터 임계값 조정 (15% → 상향)

sample28에서 12pt가 11.9%, 13pt가 18.2%, 14pt가 16.4%.
비율 필터를 20%로 올리면 13pt·14pt가 생존하지만:

**예상 문제**:

| 문제 | 설명 | 심각도 |
|------|------|--------|
| 본문 변형 오검출 | 비율이 높다 = 문서에서 많이 쓰인다 = 본문일 가능성도 높다. 비율 임계값을 올리면 실제 본문 변형(표 내 텍스트 등)이 헤더로 오분류 | 높음 |
| 다른 파일 영향 | 98개 파일에서 비율 15~20% 구간의 폰트 크기가 실제로 본문인 케이스가 존재할 수 있음. 전수 검증 필요 | 중간 |

## 4. 근본 원인

이 문제의 근본 원인은 **폰트 크기만으로 문서 구조를 추론하는 접근의 한계**에 있다.

한국어 RFP 문서의 특성:
- HWP 원본에서 스타일(제목1, 제목2 등)이 정의되어 있으나, PDF 변환 시 스타일 정보가 유실되고 물리적 폰트 속성만 남음
- 본문과 헤더의 폰트 크기 차이가 0.5~1pt인 문서가 존재
- 동일 폰트 크기 내에서 볼드/일반이 혼용
- 표, 캡션, 각주 등 다양한 요소가 헤더와 유사한 크기를 사용

**어떤 단일 규칙(임계값, 볼드, 번호 패턴)을 조정해도, 99개 파일 전체에 대한 정확도를 동시에 보장할 수 없다.** 한 파일의 검출률을 높이면 다른 파일의 오검출이 증가하는 트레이드오프.

## 5. 결론

| 항목 | 판단 |
|------|------|
| 현재 파서로 sample28 수준의 대응이 가능한가 | **아니오** — 규칙 기반 폰트 크기 파서의 구조적 한계 |
| 임계값 단순 조정으로 해결 가능한가 | **아니오** — 다른 98개 파일에 회귀 발생 |
| 복합 신호(볼드+크기+패턴) 조합으로 해결 가능한가 | **부분적** — 정확도 향상은 가능하나 false positive 완전 제거 불가, 규칙 복잡도 대폭 증가 |
| LLM 기반 접근이 필요한 영역인가 | **가능성 높음** — 문맥 이해 기반의 구조 추론이 필요한 단계 |

현재 파이프라인(v2.1.3)은 99개 중 대다수에서 정상 작동하며,
sample28과 같은 극소 gap 케이스는 **알려진 한계(known limitation)** 로 문서화하고,
향후 LLM 기반 구조 분석 또는 HWP 직접 파싱(스타일 정보 보존) 등으로 대응하는 것이 현실적입니다.
