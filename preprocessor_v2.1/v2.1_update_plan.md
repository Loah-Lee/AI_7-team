# 🚀 Korean RFP RAG 전처리 파이프라인 통합 로드맵
## Production-Ready v2.1 (Interface Contract 확정본)

본 문서는 99개 이상의 대량 RFP PDF를 안정적으로 처리하기 위한 Parser → Auditor → Chunker → Storage → Workflow 전 단계의 **구현 규격 및 데이터 생명주기를 정의한 최종 설계서**입니다.

---

## 1. Parser (parser_step1.py) – 구조 분석 및 페이지 계약 정의

* **페이지 마커 삽입 규격 (P0 계약)**:
    * Parser는 각 물리적 페이지의 **최초 텍스트 블록 이전**에 리터럴 토큰 **`[[PAGE:{page_number}]]`**를 반드시 삽입합니다.
    * `page_number`는 **1-based 실제 PDF 페이지 번호**를 사용하며, 빈 페이지가 있더라도 연속성을 유지해야 합니다.
    * 이 토큰은 Parser Raw Output 텍스트의 필수 구성 요소이며, 이후 단계의 데이터 계약을 위한 기준점이 됩니다.

* **H1/H2 계층 역전 방지 (Heuristic 보호)**:
    * **스왑(Swap) 조건**: H1 빈도 ≤ 2, 전체 헤더 대비 H1 비율 < 10%, H2 빈도가 충분히 존재할 때 수행합니다.
    * **위치 보조 필터**: 스왑 후보 H1이 **물리적 페이지 인덱스 기준 (0-based) 0~1페이지**에 존재할 때만 실행하여 정상 단일 구조 문서를 보호합니다.
    * **[한계 명시]** 본 로직은 통계적 휴리스틱 기반이며 극단적 예외 문서는 수동 검토가 필요할 수 있습니다.

---

## 2. Auditor (auditor_step2.py) – 정규화 및 마커 보존 계약

* **페이지 마커 생명주기 : 보존 (강제)**:
    * Auditor는 Parser에서 생성된 **`[[PAGE:n]]`** 패턴을 **절대 수정, 변환 또는 삭제하지 않습니다.**
    * 줄 병합, 공백 교정, 불릿 정규화 등 모든 텍스트 정제 대상에서 해당 토큰을 제외함으로써 **데이터 계약의 연속성**을 보장합니다.

* **텍스트 정제 규격**:
    * 테이블 셀 내 조건부 줄바꿈 병합을 수행하여 데이터 손상을 최소화합니다.
    * 불릿 표준화(○ ● ■ ※ → `*`)를 통해 Chunker의 가독성을 확보합니다.
    * 단일 글자 공백 교정 시 텍스트 길이 변화가 임계값을 초과하면 수정을 취소하여 원형을 보호합니다.

---

## 3. Chunker (chunker_step4.py) – 페이지 소비 및 의미 보호 분할

* **페이지 마커 생명주기 : 소비 (P0 계약)**:
    * Chunker는 Auditor를 거쳐 전달된 **`[[PAGE:n]]`** 토큰을 발견할 때마다 현재 페이지 상태를 `n`으로 갱신합니다.
    * 갱신된 정보는 각 청크의 메타데이터(`page_start`, `page_end`)로 변환되어 저장됩니다.
    * **마커 제거 정책**: 원시 마커 텍스트(`[[PAGE:n]]`)는 최종 청크 내용에서 제거할 수 있으며, 이는 이미 계산된 해시에 영향을 주지 않습니다.

* **문맥 보존 및 균형 분할**:
    * 테이블 직전 문맥을 오버랩 버퍼에 유지하여 의미 단절을 방지합니다.
    * 불릿 블록은 하나의 단위로 유지하되, **$CHUNK\_SIZE \times 0.8$을 초과**하거나 **내부 문장 수가 3개 이상**일 때만 분할을 허용합니다.
    * 작은 청크 병합 시 섹션 경로(Header Path)가 동일한 경우에만 병합을 허용합니다.

---

## 4. Storage (storage_step5.py) – 결정론 및 전면 교체 전략

* **해시 전략 (결정론적 기준)**:
    * SHA-256 해시는 **페이지 마커가 포함된 Parser Raw Output(Auditor 이전)**을 기준으로 생성합니다.
    * **[논리적 폐쇄성 보장]**: Chunker 단계에서 원시 페이지 마커 텍스트를 제거하더라도, 해시 계산은 Parser 단계 기준으로 이미 완료되었으므로 재인덱싱 판단에는 영향을 주지 않습니다.
    * Parser 로직 변경 시 해시 변경을 허용하며, 동일 로직/환경에서는 해시 안정성을 보장합니다.

* **문서 단위 전면 교체 (Upsert)**:
    * 수정 발생 시 해당 `doc_id` 전체를 단일 트랜잭션 내에서 **DELETE 후 INSERT** 합니다.

* **UID 안정성 정책**:
    * 각 청크의 UID는 **`f"{doc_id}_{local_chunk_index}"`** 형식을 사용합니다.
    * Chunker 로직 변경 시 `local_chunk_index`가 변할 수 있으며, 이는 전면 교체 전략상 **정상 동작**으로 간주합니다.

---

## 5. Workflow (preprocessor.py) – 운영 안정성 및 모니터링

* **실패 격리 및 프로세스 제어**:
    * 파일 단위 `try-except` 격리를 통해 개별 파일 오류가 전체 프로세스 중단을 유발하지 않도록 합니다.
    * `pathlib`을 통한 안전한 경로 처리와 `subprocess.run`을 사용합니다.

* **정교화된 이상 탐지 기준 (Anomaly Detection)**:
    * **데이터 불일치**: 생성된 청크 수와 최종 DB에 저장된 임베딩(Embedding) 수가 불일치할 경우 경고 로그를 발생시킵니다.
    * **처리 시간 이상 (동적/정적 병행)**:
        * **초기 구간 (처리 파일 수 $N < 10$)**: 절대 시간 임계값(예: 60초)을 Fallback으로 사용하여 이상 탐지를 수행합니다.
        * **통계 구간 (처리 파일 수 $N \ge 10$)**: 이전 파일들의 평균 처리 시간 대비 **3배를 초과**할 경우 경고 로그를 출력합니다.
    * **즉시 실패 처리**: 생성된 청크 수가 **0**인 경우 해당 파일을 즉시 실패 처리하고 요약 보고서에 기록합니다.

* **운영 지표 기록**: `execution_summary.csv`에 처리 시간, 청크 수, **생성된 임베딩 수**, 재인덱싱 여부 등을 기록합니다.

3. **페이지 추적**: Chunker가 마커를 **소비**하여 메타데이터에 반영하고, 내용에서 제거 시 해시 독립성을 유지하는가?
