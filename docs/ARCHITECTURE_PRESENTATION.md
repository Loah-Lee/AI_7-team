# 입찰메이트 아키텍처 발표 스크립트

## 0.1 3분 요약 버전 (쉽게 설명할 때)
### 3줄 핵심
- 질문이 들어오면 먼저 "빠르게 답할 수 있는 질문인지"를 판단합니다.
- 빠르게 가능하면 CSV에서 즉답하고, 아니면 문서를 검색해서 근거를 확인합니다.
- 근거가 충분할 때 답변하고, 부족하면 부족하다고 말해 환각을 줄입니다.

### 3분 발표 멘트
"저희 아키텍처는 어렵게 말하면 RAG지만, 실제 동작은 단순합니다.  
첫째, 질문을 이해합니다. 둘째, 간단한 질문은 CSV에서 바로 답해 속도를 확보합니다.  
셋째, 복잡한 질문은 문서를 검색하고 근거를 확인한 뒤 답변합니다.  
그래서 빠른 질문은 빠르게, 어려운 질문은 근거 중심으로 안정적으로 답할 수 있습니다."

## 0. 발표 목표
- 질문: "이 시스템이 어떻게 빠르고 정확하게 답하느냐?"
- 답: `질의 해석`, `하이브리드 검색`, `근거 중심 응답` 3단 아키텍처로 해결한다.

## 1. 발표 구성 (약 7~10분)
1. 문제 정의와 설계 원칙 (1분)
2. 시스템 구조도 설명 (2분)
3. 질의 처리 시퀀스 설명 (2분)
4. 정확도/속도 트레이드오프 포인트 (1~2분)
5. 데모 시나리오 (2분)
6. 마무리 (30초)

## 2. 오프닝 멘트 (그대로 읽기)
"저희 시스템은 RFP 문서 질의응답에서 가장 큰 두 가지 문제인 속도와 정확도를 동시에 해결하는 구조로 설계했습니다.  
핵심은 질문을 먼저 구조화하고, 검색은 렉시컬로 후보를 좁힌 다음 벡터로 의미 재정렬하며, 마지막 답변은 반드시 근거를 중심으로 생성하는 점입니다."

## 3. 시스템 구조도 설명 (docs/ARCHITECTURE.md 첫 번째 그림)

### 설명 순서
1. `UI`: Streamlit에서 질문을 받는다.
2. `Workflow`: `RAGChatbotV17`가 전체 오케스트레이션을 담당한다.
3. `Graph Layer`:  
   - `QueryIntentParser`: 질문 의도 해석  
   - `QuestionPlanner`: 질문이 요구하는 슬롯 정의  
   - `AnswerGenerator`: 필요 시 생성형 답변 수행  
   - `ConversationContext`: 후속질문 문맥 유지
4. `Retrieval Layer`:  
   - `VectorStore` + Chroma  
   - 하이브리드 검색(lexical prefilter -> vector rerank)
5. `Parser Layer`: CSV/PDF/HWP를 공통 검색 가능한 형태로 변환한다.
6. `Config/Prompt`: 운영 모드/튜닝 변수와 프롬프트 정책을 중앙 관리한다.

### 발표 멘트
"구조적으로는 Workflow가 중심이고, 그 아래 질의 해석, 검색, 생성이 분리되어 있습니다.  
이렇게 계층을 분리해두면, 속도 이슈는 Retrieval에서, 정확도 이슈는 Planner/Extraction에서 독립적으로 튜닝할 수 있습니다."

## 4. 질의 처리 시퀀스 설명 (docs/ARCHITECTURE.md 두 번째 그림)

### 단계별 설명
1. `answer(query)` 호출
2. 의도 파싱 및 질문 계획 생성
3. CSV short-circuit 가능 여부 검사
4. 즉답 불가 시 하이브리드 검색 실행
5. 근거 검증(비교 질문 커버리지 포함)
6. extractive 우선 응답, 부족 시 생성형 보완
7. 최종 payload 반환(`answer`, `source_type`, `confidence`, `evidence`)

### 발표 멘트
"핵심은 검색 이후에 바로 생성하지 않는다는 점입니다.  
먼저 근거를 점검하고, 근거가 충분하면 extractive로 답해 안정성을 높입니다.  
근거가 부족할 때만 생성형을 쓰는 방식으로 환각을 줄입니다."

## 5. 기술적 차별점 (한 장으로 요약)

### 5.1 속도
- 구조화 질문은 CSV short-circuit로 즉시 응답
- 검색 예산(`RETRIEVAL_MAX_HYBRID_CALLS`)으로 과도한 확장 방지

### 5.2 정확도
- 렉시컬 1차 필터링 후 벡터 재정렬
- 정밀 사실 질의(숫자/단위/문자셋/기한)는 앵커 근거 검증
- 비교 질문은 기관별 커버리지 확인 후 응답

### 5.3 운영성
- 설정값(`src/utils/config.py`)으로 모드 전환 가능
- `ANSWER_QUALITY_MODE`로 balanced/accurate 운영 분리

## 6. 데모 시나리오 (실전 발표용)

### 시나리오 A: 구조화 질의
- 질문: "고려대학교 사업비는 얼마인가요?"
- 기대 포인트: CSV short-circuit로 빠른 응답

### 시나리오 B: 비교 질의
- 질문: "A 기관과 B 기관 요구사항 차이를 비교해줘"
- 기대 포인트: 기관별 근거 수집 후 비교 응답

### 시나리오 C: 정밀 사실 질의
- 질문: "문자셋은 무엇인가요? UTF-8인가요?"
- 기대 포인트: 해당 키워드 근거 라인 중심으로 응답

### 데모 멘트
"같은 파이프라인이지만 질문 유형에 따라 가장 안전한 경로로 자동 분기됩니다.  
그래서 단순 질의는 빠르고, 복합 질의는 근거 중심으로 정확하게 답합니다."

## 7. 예상 질문과 답변

### Q1. 왜 벡터 검색만 쓰지 않고 렉시컬을 먼저 쓰나요?
A. 정밀 질의는 토큰 일치가 매우 중요하기 때문에, 렉시컬로 후보를 좁히면 오탐이 줄고 비용도 절감됩니다.

### Q2. 환각은 어떻게 통제하나요?
A. extractive 우선, 비교 커버리지 검증, 정밀 사실 앵커 검증으로 생성 전에 근거를 확인합니다.

### Q3. 운영 중 튜닝은 어렵지 않나요?
A. `config`의 ENV 중심 구조라 코드 수정 없이 모드/예산/검색 파라미터를 조정할 수 있습니다.

## 8. 클로징 멘트 (30초)
"정리하면, 저희 아키텍처는 단순히 검색-생성 체인이 아니라 질문 유형별로 최적 경로를 선택하는 오케스트레이션 구조입니다.  
그 결과, 빠른 응답과 근거 기반 정확도를 동시에 달성할 수 있고, 운영 환경에서도 설정만으로 안정적으로 튜닝할 수 있습니다."
